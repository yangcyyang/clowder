# PPT Agent

把“模糊需求 + 资料”先变成可确认的页面计划，再交给后续 PPT 写作、设计和制作。MVP 不追求一口气出成稿，先验证三段链路稳定。

## 核心原则

```text
模糊需求 + 资料
  → Stage 1: Brief 补齐
  → Stage 2: 资料理解
  → Stage 3: 页面计划生成
  → Stage 4: 双层蓝图 MD（给人审 + 给 Agent 执行）
  → 用户确认
  → 后续写作 / 设计 / 制作
```

AI 不直接写 PPT。先判断这份 PPT 要解决什么问题，再判断资料能支撑什么，最后规划每一页讲什么、凭什么讲。

## Stage 1: Brief 补齐
**输入**：用户的模糊需求。

**MVP 必填 3 项**：
- 受众：给谁看？
- 场景：汇报、培训、提案、路演、复盘、方案评审？
- 目标：希望对方看完后理解什么、认可什么或做什么决定？

**可暂定项**：页数、语气、必须使用资料、成功标准。可以合理假设，但必须标注“暂定”，不能伪装成用户已确认。

**交互规则**：
- 一次最多问 3-5 个问题。
- 先补齐受众、场景、目标，再进入资料理解。
- 用户答不全时，输出 Brief 摘要 + 暂定假设，让用户改。

## Stage 2: 资料理解

**输入**：已确认或可暂定的 Brief + 用户资料。

**禁止**：不要写 PPT 正文，不要直接生成页面标题，不要为了放资料而堆料。

**轻量输出**：
- 资料主要讲什么。
- 哪些内容可以作为证据。
- 是否存在明显冲突、缺口或缺少数据支撑。

资料编号用 `M1/M2/M3...`，后续页面计划必须引用这些编号。

## Stage 3: 页面计划生成

**输入**：Brief + 资料理解结果。

**MVP 必填 4 项**：
- 页码
- 页面标题
- 核心观点（一页只讲一件事）
- 依据资料（如 `M1/M2`）

**可选增强**：建议视觉、缺失信息。资料不足时必须标注缺口。

**输出模板**：

```markdown
## Brief 摘要

| 字段 | 内容 | 状态 |
|---|---|---|
| 受众 | ... | 已确认/暂定 |
| 场景 | ... | 已确认/暂定 |
| 目标 | ... | 已确认/暂定 |

## 资料理解

| 编号 | 核心用途 | 可用证据 | 冲突与缺口 |
|---|---|---|---|
| M1 | ... | ... | ... |

## 页面计划

| 页码 | 页面标题 | 核心观点 | 依据资料 | 建议视觉 | 缺失信息 |
|---:|---|---|---|---|---|
| 1 | ... | ... | Brief/M1 | ... | ... |
```

## Stage 4: 双层蓝图 MD

**触发**：用户要求“形成 MD”“结构设计蓝图”“给人看 + 给 Agent 看”“先确认内容再制作”。

输出必须分两部分：
- **Part 1：给人看的 PPT 内容稿**：逐页写页面类型、标题、正文全文。
- **Part 2：给 Agent 的制作执行稿**：逐页写 pageKey、layoutType、本页目的、布局、排版、色彩、图片槽位、验证规则。

**Part 1 规则**：
- 只写观众能在 PPT 上看到的内容，不写“本页目的”“视觉建议”“生成注意”等编辑说明。
- 目录页只放短标题/短问题，通常 3-5 条；每条尽量控制在 18 个中文字以内。
- 章节页只放 1-2 句过渡判断，不放列表、不放长解释、不放元描述。
- 正文页可以写完整段落，但必须是观众可读的页面正文，不是作者备注。

**Part 2 规则**：
- 页面类型、布局、排版、色彩、图片槽位、验证规则都放这里。
- 图片槽位要说明用途和备选方案；需要生成图片时再交给 image-generation。
- 对齐当前 PPT Agent 链路：`textContent.body` 存正文全文，`bullets` 存页面上要强调的短句，`layoutType/styleConfig` 存制作规范。

## 与现有 PPT Agent 的关系

- 当前 E2E 真相源仍是 `test_simple_3pages.py`，链路是 `Clarify → Outline → SVG → PPTX`。
- MVP skill 先规范产品工作流，不直接改业务代码。
- 进入实现时，Stage 3 应对齐现有端点：`/api/clarify`、`/api/generate/outline`、`/api/generate/page-plans`，以及项目产物 `page_plans.json/html`。
- Stage 4 的 Part 1 对应 `slidePlan.textContent`，Part 2 对应 `layoutType/styleConfig` 与后续 `svg-design` 输入约束。

## Common Mistakes

| 错误 | 后果 | 修复 |
|---|---|---|
| 直接叫“生成大纲” | 退化成标题列表 | 改成页面计划：每页观点 + 依据 |
| Brief 表过重 | 用户不愿填，MVP 变慢 | 必填只保留受众/场景/目标 |
| 资料理解时写正文 | 阶段混乱，后续难确认 | 只提取用途、证据、冲突和缺口 |
| 页面没有依据资料 | 变成拍脑袋结构 | 每个核心观点必须引用 `M#` |
| 一页塞多个观点 | PPT 难读难讲 | 一页只让观众记住一件事 |
| 把目录页写成长段落 | 目录变成正文页，视觉上拥挤 | 目录页只放短问题/短标题 |
| 把章节页写成解释页 | 节奏页失去停顿感 | 章节页只保留 1-2 句过渡判断 |
| 把本页目的写进 Part 1 | 观众看到编辑说明 | 本页目的、布局、验证规则全部放 Part 2 |

## 和其他 skill 的区别

- `ppt-forge`：负责 PPT 内容规划后续的风格定调、Slide 制作、视觉审查和导出验证。
- `writing-skills`：负责创建或修改 skill 本身。
- `tdd` / `worktree`：负责把该工作流落到代码实现。

## 下一步

页面计划确认后 → `ppt-forge` 做后续 PPT 写作、设计和导出；需要落地到代码时 → `writing-plans` / `worktree` / `tdd`。
