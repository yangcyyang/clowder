# Batch Confirm Gate — 批量操作确认门禁

## 核心知识

批量操作最容易出的两类事故：**漏判**（规则没覆盖到的文件被误动）和**抢跑**（没等到人确认就执行）。
这个流程把"判断"和"执行"拆成两个独立、可审计的阶段，中间插一道人工确认闸。

## 流程

```
Step 1: 拆规则 — 把任务拆成若干条"可判定条件"
  - 每条规则必须能对单个对象给出是/否答案（后缀、日期、路径、命名等）
  - 规则里出现"合适的""大概""看情况"这类模糊词 → 先追问澄清，不能自己脑补标准
  - 明确排除条件（黑名单关键词、白名单路径等）也算一条规则

Step 2: 扫描 — 逐项对每个候选对象核对规则，产出《待处理清单》
  - 清单格式：对象名 + 每条规则的判定结果（✅/❌）+ 综合结论（动 / 跳过 + 原因）
  - 综合结论必须能从逐条判定推出来，不能只写结论不写依据
  - 清单发给委托人，不先动手

Step 3: 等确认 — 停在这里，不执行
  - 必须等到委托人明确的确认信号（如"确认"）才能进入 Step 4
  - 没回复、已读不回、或只是追问细节，都不算确认
  - 委托人对清单提出修改 → 回到 Step 2 用新意见重新出清单，再等确认

Step 4: 执行 — 按确认后的清单动手
  - 只处理清单里标记为"动"的对象；清单外的对象不碰
  - 执行中遇到清单没覆盖的情况（对象消失、权限不足等）→ 停下来，计入报告的异常项，不擅自扩大处理范围

Step 5: 报告 — 输出执行结果
  - 动了哪些：对象 + 具体操作
  - 跳过了哪些：对象 + 命中的排除/未满足规则
  - 异常/未处理：对象 + 原因
```

## Quick Reference

| 阶段 | 产出 | 谁来推进 |
|------|------|----------|
| 拆规则 | 可判定条件列表 | 执行者，规则模糊则先问委托人 |
| 扫描 | 待处理清单（逐项判定+结论） | 执行者 |
| 等确认 | 无（停住） | 委托人给出明确确认 |
| 执行 | 实际操作 | 执行者，只动清单内对象 |
| 报告 | 动了/跳过/异常三分类结果 | 执行者 |

## Common Mistakes

| 错误 | 后果 | 修复 |
|------|------|------|
| 清单只给结论不给逐条判定依据 | 委托人没法核实规则用对没有 | 每个对象必须列出每条规则的✅/❌ |
| 没等到"确认"就先执行 | 抢跑，误删/误改无法挽回 | Step 3 是硬停点，没有明确确认信号不进 Step 4 |
| 把"没回复"当成默认同意 | 同上 | 只有委托人明确给出确认词才算数 |
| 执行时顺手处理了清单外的对象 | 扩大了授权范围 | 只动清单里标"动"的项，多余发现另开清单 |
| 报告只给汇总数字（"清理了 12 个"） | 委托人没法核对具体动了什么 | 报告必须逐项列出对象名 + 操作/原因 |
| 规则含糊（"看着不需要的"）直接开始扫描 | 判定标准因人而异，结果不可复现 | Step 1 先把规则拆到可判定，含糊就先追问 |

## 和其他 skill 的区别

- `careful`（gstack）：执行危险命令前的警告提示，是单点拦截，不含"扫描出清单"和"结果报告"的完整闭环。
- `quality-gate`：代码交付前的自检门禁，检查对象是 spec/AC，不是批量候选对象清单。
- 本 skill 专用于**有一批候选对象、规则可拆解、需要人工确认后再动**的场景。

## 下一步

清单确认后执行完 → 直接给报告，不需要再进入其他 skill；如果批量操作涉及代码改动，执行完后按需过 `quality-gate`。
