# 交付自动化与打法手册

## R — 原文 (Reading)

> "给客户交付自动化，是产品本身；让自己的交付工作自动化，是效率。……FDE 的日常工作中，有惊人比例的动作是可模板化的重复劳动：新客户的部署环境初始化、数据接入的标准管道、安全审查的问卷应答、上线前的检查清单、周期性向客户汇报的格式。每一个第二次做的动作，都应该触发一个提问：『这能变成脚本、模板或清单吗？』"
>
> — 范冰《前线部署工程师》4.7

---

## I — 方法论骨架 (Interpretation)

交付自动化是 FDE 团队摆脱"收入随人头线性增长"的第一杠杆。核心逻辑：

1. **每个第二次做的动作，都应触发提问**："这能变成脚本、模板或清单吗？"
2. **四类资产**：部署模板（一键式基础设施代码）/ 集成组件库（写一次处处复用）/ 检查清单文化（安全审查/上线准入/撤场交接清单）/ 自动化汇报（周报、现场情报半自动生成）
3. **人海的本质不是人多，而是每个人都在做不可复用的一次性劳动**——当每次交付都为下一次修路，人海就成了会自我加速的机器

配套打法手册三属性：
1. **长在流程里，不躺在知识库里**——嵌入工作流：尽调阶段自动弹清单、部署阶段清单是硬关卡、复盘阶段手册更新是必填产出
2. **按"场景"而非"功能"组织**——按客户场景写（"金融反洗钱场景打法""制造业排产场景打法"），每场景七件套：典型痛点与契合检验要点 / 尽调清单 / 数据与集成雷区 / 评估与验收指标模板 / 变革管理角色地图 / 计价与扩容参考结构 / 历史复盘教训库
3. **必须"活"**——有负责人、有版本、有折旧；没有负责人的手册会在一年内腐烂成误导新人的陷阱，比没有手册更糟

手册记录"判断"，组件库沉淀"手艺"，平台固化"能力"——三者齐备，新 FDE 小队两周内达到老团队八成战斗力。

## A1 — 书中的应用 (Past Application)

### 案例1: Decagon 15 天部署
- **问题**: 怎么把部署周期压到极致？
- **方法论的使用**: 高度模板化的接入层（部署模板资产）
- **结论**: 简单场景部署压到 15 天
- **结果**: 成为交付自动化的标杆数据

### 案例2: Palantir 本体 = 组件库极致
- **问题**: 怎么让数据接入可复用？
- **方法论的使用**: 数据接入的产物不是一次性管道，而是可复用的、带业务含义的数据资产
- **结论**: 本体模型把组件复用做到极致
- **结果**: 支撑毛利率 82%（比绝大多数"纯软件"公司还漂亮）

### 案例3: Harvey 场景手册
- **问题**: 律所场景打法怎么复制？
- **方法论的使用**: 把第一个客户（年利达）的经验写成可继承的场景资产
- **结论**: 打法能复制到普华永道、佳利
- **结果**: 从 1 家律所到 1300 家组织

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 交付团队重复劳动多、效率低
2. 新客户进场要从零配置环境，周期长
3. 需要把项目经验沉淀成可复用资产
4. 团队扩张但产能跟不上

### 语言信号

- "每次新客户都要从零搭环境，太累了"
- "我们的打法手册写了没人看"
- "怎么让交付团队效率翻倍？"
- "怎么摆脱人海战术？"

- 与 `deployment-activation`：激活是客户侧行为改变，自动化是供给侧效率提升

## E — 可执行步骤 (Execution)

1. **盘点重复劳动**
   - 完成标准：列出 FDE 日常工作中"第二次做的动作"清单（部署初始化/数据接入/安全问卷/上线检查/汇报格式）
   - 判停条件：清单少于 5 项 → 盘点不完整，按 4.7 的资产类型逐项过

2. **建四类资产**
   - 完成标准：至少产出——1 个部署模板（一键拉起环境）/ 1 个组件（连接器或评估框架）/ 3 张检查清单（安全/上线/撤场）/ 汇报半自动模板
   - 判停条件：资产建了但没人用 → 检查是否嵌入流程（见步骤 3）

3. **把资产嵌进工作流**
   - 完成标准：尽调阶段自动弹出清单、部署阶段清单是硬关卡、复盘阶段手册更新是必填产出
   - 判停条件：资产只在文档系统里能搜到 → 等于不存在（文档坟场）

4. **写/维护场景打法手册**
   - 完成标准：按客户场景组织（非按组织结构），每场景七件套齐备
   - 判停条件：手册没有负责人/版本/折旧机制 → 会腐烂成陷阱
   - 备注：每个项目结束后强制回看更新，每半年整体检修

5. **衡量复用率**
   - 完成标准：统计新项目复用已有资产的比例，目标逐季上升
   - 判停条件：复用率不升 → 回流机制没生效（衔接 scale-copy）

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 一次性任务（只做一次的动作不值得沉淀，先做再复盘）
- 纯产品研发（无交付语境）

### 书中警告的失败模式

- 手册写成"写完即死"的文档坟场——不嵌入流程等于不存在
- 按公司组织结构写手册（"交付流程""技术规范"）而非按客户场景
- 手册没有负责人：一年内腐烂成误导新人的陷阱
- 每个第二次的动作不触发自动化提问——人海战术永续

### 作者的盲点 / 时代局限

- 自动化资产的前期投入（建模板/组件）需要团队有富余产能，小团队可能"忙到没时间自动化"——需要刻意安排
- 2026 年 AI 编码工具让模板生成更便宜，但"哪些动作值得自动化"的判断仍靠人

### 容易混淆的邻近方法论

- 不是"外包/人海"——自动化是替代重复劳动，不是转移
- 不是"产品化"——交付自动化是内部效率，产品化是客户可配置能力（scale-copy）
