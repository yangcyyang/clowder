# 问题-方案契合检验（PSF 三关）

## R — 原文 (Reading)

> "PMF 问『我的产品有没有市场要』，视角在供给方；PSF 问『客户这个具体的问题，值不值得、能不能被我们的能力解决』，视角在需求方。一个企业客户内部，可能有几百个『人工智能能做点什么』的机会点，但真正值得做的，必须同时过三关。"
>
> — 范冰《前线部署工程师》2.2

---

## I — 方法论骨架 (Interpretation)

PSF（Problem-Solution Fit）是一个前置决策框架：在投入任何工程资源之前，判定"这个客户的具体问题"是否值得被解决。核心逻辑：

1. **视角在需求方**——不是"我的产品能做什么"（PMF），而是"这个客户的问题值不值得"（PSF）
2. **三关缺一不可**——痛点、经济性、可行性全过才算契合；任何一关不过，立即停止或换问题
3. **必须在现场过**——坐总部会议室对着二手信息判断，是大多数错误问题的来源
4. **企业里错误问题的密度远超想象**——几百个"AI 能做的事"里真正值得做的很少

三关详解：
- **痛点关**：是不是某个具体的人的具体的痛？（两个"具体"）"提升客服效率"是方向不是痛点；"客服主管每周一花三小时从四个系统手动汇总工单"才是痛点
- **经济性关**：解决这个问题值多少钱？（每周吃掉多少人时？出错赔多少？省下的人手能干什么？）
- **可行性关**：以现在的能力和数据现实，能做到几分？（数据在哪、什么状态？准确率门槛是多少？）

## A1 — 书中的应用 (Past Application)

### 案例1: MIT 报告的预算错配
- **问题**: 企业 AI 预算花哪了？
- **方法论的使用**: 超过半数企业 AI 预算投向前台销售营销，回报却集中在后台合同审查、采购、风控
- **结论**: 大家在解决"演示效果好的问题"，而不是"值钱的问题"
- **结果**: 用经济性关可以筛掉这类错配

### 案例2: Palantir 训练营的经济性前置
- **问题**: 如何避免客户项目不赚钱？
- **方法论的使用**: 训练营把经济性关前置——客户开始前锁定"核心战场"、给出量化靶子
- **结论**: "排产冲突降低 30%""库存周转缩短 15%"这种靶子，逼着双方先过经济性关
- **结果**: 销售周期从 9-12 个月压到数周

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 客户/老板提出一个"AI 需求"，需要判断要不要接/要不要做
2. 一个项目做了一半发现方向可疑，需要回看问题定义
3. 在多个候选项目/需求之间排序，决定先做哪个
4. 写提案或验证方案前，先确认问题值得解决

### 语言信号

- "客户想要一个智能客服"
- "这个需求值不值得做？"
- "老板说要数字化转型，从哪里下手？"
- "AI 项目怎么做才能不翻车？"

### 与相邻 skill 的区分

- 与 `poc-rejection`：PSF 问"这个问题值不值得做"，拒绝机制问"这个项目该不该接"（PSF 是接单前的问题判断，拒绝机制是接单后的风险控制）
- 与 `shadow-work`：PSF 是筛选，影子工作法是找到 PSF 需要的真实痛点

## E — 可执行步骤 (Execution)

1. **把需求翻译成"具体的人的具体的痛"**
   - 完成标准：能说出"谁 + 什么频率 + 多痛 + 现在怎么对付"
   - 判停条件：只能说出方向（如"提升效率"）→ 问题定义不合格，先做影子工作法
   - 高级标准：这是否是 CEO 最关注的五个问题之一（麦格鲁标准）？

2. **算经济账**
   - 完成标准：写出"这个问题每周吃掉多少人时 × 人力成本 = 年化价值"的粗算
   - 判停条件：算不出价值或价值太低 → 标记为"真痛但不值钱"，停止或换问题
   - 参考：Palantir 训练营的做法是让客户先给量化靶子

3. **查数据与能力现实**
   - 完成标准：回答两个问题——数据在哪、什么状态？准确率门槛是多少？
   - 判停条件：数据分散在七个系统且无权威源 → 可行性存疑，成本要重估
   - 关键判断：很多业务场景 90% 加人工复核就是最优解，别追求 99%

4. **三关汇总裁决**
   - 完成标准：明确回答"过/不过"，并写出每关的证据（一句话）
   - 输出：三关都过 → 进入 MVD/提案阶段；有不过的 → 要么换问题，要么先补短板

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 问题已经明确锁定、团队已在执行中（PSF 是前置决策，执行期该用热修复/评估体系）
- 纯技术选型或架构设计问题（不是"问题值不值得做"）

### 书中警告的失败模式

- 把"痛点"写成方向："提升客服效率"不是痛点
- 跳过经济性关：做了真痛但不值钱的项目，活不过下一个预算季
- 可行性被热情淹没：现场回答"数据在哪、什么状态"时，答案经常比想象糟
- 坐在总部做判断：三关必须在客户现场过

### 作者的盲点 / 时代局限

- "CEO 最关注的五个问题"标准在国央企/ToG 场景可能失真（决策链不同）
- PSF 对"数据现实"的悲观假设（七个系统三个版本）在 2026 年因 AI 集成工具开始缓解，可行性关的门槛在下移

### 容易混淆的邻近方法论

- 不是 PMF（产品-市场契合）——那是供给方视角
- 不是"需求调研"——那是问客户要什么，PSF 是判断值不值得做
