# 部署激活六件武器

## R — 原文 (Reading)

> "企业软件的『上线』，走完的只是采购和验收的行政流程；『激活』发生在用户的行为里。上线那天可以庆祝，但项目成不成，要看三个月后还有没有人用。……激活是 FDE 的主场，也是它跟『交付即走』的传统实施最大的不同：传统实施把验收单当终点，FDE 把客户行为的改变当终点。"
>
> — 范冰《前线部署工程师》4.1

---

## I — 方法论骨架 (Interpretation)

激活 = 目标用户群体在日常工作中形成对系统的稳定使用习惯（三个月后没人催、系统依然被高频使用）。激活要过三道关：顺手（比旧习惯多一步就没人用）、可信（错一次信任清零）、相关（与己无关没人碰）。

六件武器（对应六个子方法论）：
1. **热修复（速度）**——部署期迭代以天/小时计：反馈直达写代码的人 / 优先级按"使用阻塞度"而非功能重要度 / 每天收工问"今天的改动让用户明天的哪一刻更顺了"
2. **评估体系（方向感）**——用标准案例给 AI 输出持续打分：从真实案例长出来 / 让业务方当评委 / 接生产回路（分数下滑告警）。"把老师傅脑子里那句什么叫好，变成系统天天自动执行的打分标准"
3. **降门槛（巧劲）**——四手法：寄生已有界面（表格/邮件/工单） / 默认值预装第一次使用 / 把"问 AI"翻译成"点按钮" / 先做副驾驶再谈自动驾驶
4. **集成战争（耐性）**——当战役打不当杂务办 / 数据问题先于模型 / 用 AI 打 AI 的集成 / 知道何时绕开（影子读取/人工摆渡/宣告隔离）
5. **变革管理（软功）**——三组人物经营：支持者（给材料/战功/安全感）、影响者（第一批试用/认真对待吐槽/采纳显性化）、受损者（提前设计出路/不裁员承诺/守门人转型教练）
6. **交付自动化（杠杆）**——四类资产：部署模板 / 集成组件库 / 检查清单文化 / 自动化汇报

核心逻辑：**上线 ≠ 激活**；企业部署死在用户手里（不顺手/不可信/无关），没有一关能在总部解决，只能到客户的会议室、车间和工位上去过。

## A1 — 书中的应用 (Past Application)

### 案例1: 西班牙对外银行（降门槛+激活）
- **问题**: 12 万员工怎么激活？
- **方法论的使用**: 先发 3300 个账号不做全员运动，从员工已有的 ChatGPT 界面切入；管理层不禁止影子 AI 反而提供安全平台
- **结论**: 让习惯自己走路——从 3300 到 11000 再到 120000，每一步都发生在上一步使用数据公布后
- **结果**: 83% 员工每周活跃，人均每周省约 3 小时

### 案例2: OpenAI × 约翰迪尔（评估体系先行）
- **问题**: 怎么保证 AI 输出质量方向对？
- **方法论的使用**: 先和农艺师评审数百个真实作业案例、建定制评估体系，再快速迭代模型，赶上农时
- **结论**: 先定"什么叫好"，模型优化才有方向
- **结果**: 化学品使用减少最高 70%，农户互动频率提升 6 倍

### 案例3: Vivid Seats × Sierra（变革管理全员动员）
- **问题**: 激活期怎么让客户组织动起来？
- **方法论的使用**: 产品、客户体验、工程三团队全部压上，"一旦做了决定就百分之百投入"
- **结论**: 启动到上线不到四周
- **结果**: 自助解决率提升 40%，客户满意度提升 35%；常规问题被接走后团队转向根治流程问题

### 案例4: 得物 AI 转型（变革管理顺序）
- **问题**: 万人规模公司 AI 转型怎么推？
- **方法论的使用**: 三步——先共识（降门槛让人用起来）→ 再场景（按容错空间分四象限，容错大的优先）→ 后知识（知识运营小组搬专家隐性经验）
- **结论**: 共识、场景、知识——顺序不能反
- **结果**: 成为书中中国样本

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 系统上线了但没人用 / 使用率低
2. 部署期如何快速迭代、保证质量方向
3. 员工抵触新系统，需要变革管理
4. 如何提高企业系统的激活率

### 语言信号

- "系统上线三个月了没人用"
- "用户说界面不好用/不顺手"
- "员工不愿意用新系统怎么办？"
- "部署期怎么保证 AI 输出质量？"

### 与相邻 skill 的区分

- 与 `mvd-validation`：MVD 是验证价值（上线前），激活是让行为改变（上线后）
- 与 `retention-defense`：激活让项目活过第一年，续约守卫让它长期活下去

## E — 可执行步骤 (Execution)

1. **诊断激活三关**
   - 完成标准：判断系统死在哪一关——不顺手（门槛）/ 不可信（质量）/ 无关（价值感）
   - 判停条件：没有使用数据 → 先埋点/观察再诊断
   - 参考：双轨制信号（官方系统空转、影子 AI 横行）

2. **立热修复机制**
   - 完成标准：反馈直达写代码的人 + 迭代按"使用阻塞度"排序 + 每天收工问"明天哪一刻更顺"
   - 判停条件：反馈还要经客户成功/产品经理转手 → 机制没立起来

3. **建评估体系**
   - 完成标准：评估集来自真实业务语料 + 业务方当评委 + 接到生产回路（下滑告警）
   - 判停条件：评估集是工程师编的 → 回炉

4. **降门槛四手法逐一排查**
   - 完成标准：寄生已有界面 / 默认值预装 / 高频场景按钮化 / 高风险流程先副驾驶
   - 判停条件：要求用户登录全新门户 → 违反寄生原则，改

5. **变革管理三角色经营**
   - 完成标准：支持者（材料/战功/安全感）+ 影响者（第一批试用/吐槽认真对待/采纳显性化）+ 受损者（新生路预案）
   - 判停条件：没有识别受损者 → 政治地图没画（回 site-due-diligence）

6. **沉淀交付自动化**
   - 完成标准：每个"第二次做的动作"问"能变脚本/模板/清单吗？"——产出部署模板/组件/检查清单/自动化汇报
   - 判停条件：同一件事每次手动做 → 自动化杠杆没用上

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- 问题还没定义时（用 psf-screening/shadow-work）
- 续约谈判期（用 retention-defense）

### 书中警告的失败模式

- 把验收单当终点：交付即走，撤场即冷（伴舞式激活）
- 反馈隔传话筒：每传一手丢一半上下文，等排上期用户心也凉了
- 评估集工程师自嗨：业务方没参与，"好"的定义失真
- 要求用户登录新系统：多一次登录激活率流失一截
- 忽视受损者：他们成为系统最顽强的地下抵抗者

### 作者的盲点 / 时代局限

- 六件武器偏"ToB 现场"语境，纯远程交付场景（2026 年混合交付占比上升）部分武器需降级适配
- 变革管理的"不裁员承诺"在客户强势/成本压力大时可能无法兑现，需提前评估客户承诺力

### 容易混淆的邻近方法论

- 不是"上线"——上线是行政流程，激活是行为改变
- 不是"培训"——培训是激活的手段之一（分层培训），激活是结果
