| 指标 | 数值 |

`historyBudgetRatio > 100%` 意味着：**历史全量文本的 token 数已超过模型最大 context window**。系统通过自动裁剪在续接时截断，但每次 resume 前仍要重新加载全量历史 → 产生大量 cache read。

## 七、优化建议

### P0 — 立即生效 (不改代码)
1. **轻量猫规则裁剪**: Pi 的 System Prompt 应使用精简版 — 去掉花名册全文和任务门禁，只保留 3 条核心规则 (≤500 tokens)。当前 5,825 token 固定注入对 90 token 实际 input 是 64 倍浪费。

### P1 — 短期 (1-2 天)
2. **启用历史压缩 (shadow-summary)**: 当前全部 `observe` 模式，`historyBudgetRatio` 动辄 174~436%。切换到 `shadow-summary` 可将历史从数十万 token 压缩到几千 token 摘要，对中量猫 (芝芝/宪宪) 效果显著。
3. **Codex session 分片续接**: gpt52 每轮 58M input 中 93% 是 cache，虽不计费但增加了延迟。考虑为超长 session 引入自动分片或 fresh-start 策略。

### P2 — 中期 (1 周)
4. **固定注入按猫分级**: 为 Pi/点点/kimi 提供 `minimal` 模式 System Prompt，去掉花名册、A2A 派工上下文、会话连续性提示。仅保留 Skill Router 入口 + 角色简述。
5. **查询分页**: `/api/run-ledger` 的 `scanAll()` 当前全量扫描 Redis → 应为频繁查询的 endpoint 加分页。
6. **Kimi token 统计接入**: Kimi 提供商的 token 计数未纳入，导致显示 0 output。需在 Kimi 提取路径中补上 token 统计。

### P3 — 长期 (backlog)
7. **固定注入 lint 拦截**: 已在 BACKLOG F002 — "发送前 lint：检测交棒语句缺行首 @ 时拦截提示"，可扩展为检测固定注入膨胀告警。

## 八、v1.1 对账修正记录

v1.0 报告存在两处数据污染，v1.1 已修正：

### Bug 1: per-cat 成本双计
**根因**: 表一/表六的 per-cat 成本取自 `/api/run-ledger` 的 `usage.costUsd`，按 `targetCats[]` 逐猫累加。当一次 invocation 有多个 target cats（如 `['opus-45', 'codex']`），同一个 `$6` 成本被计入两只猫的桶 → 双计。

**修正**: 全表改用 `/api/usage/daily` 数据（`usageByCat` 按猫归因，无重复）。

### Bug 2: 合计成本偏小
**根因**: 报告合计 `$145.41` 仅来自少数 thread 的 ledger，而 daily API 扫描 Redis 全量。差额 `$43.62` 来自其他 thread 的 Claude 调用。

**修正**: `$145.41` → `$189.03` (daily API grand total)。

## 九、数据局限

- **sourceBreakdown (按源分拆)**: 当前 API 返回的 usage 数据未包含 `sourceBreakdown` 字段，固定注入占比为代码级估算，非实测值。
- **Kimi 统计缺失**: Kimi provider 的 token usage 未写入 `usageByCat`，0 output 不代表没有调用产出。
- **Pi cache 异常**: `cacheReadTokens > inputTokens` 表明存在多猫共享的 cache 归因问题，需后端排查。
- **Run-ledger vs daily API 口径差异**: run-ledger 按 `startedAt` 分桶，daily API 按 `usageRecordedAt` 分桶，参与次数和成本会有小偏差。
