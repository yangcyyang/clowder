Clowder AI 本地架构与进度说明

这份文档基于当前本地仓库和《multi-agent 课程》整理。核心判断是： Clowder 已经不只是多 Agent 编程工具，而是在走向“可领养、可治理、可迁移、可成长的 AI 团队操作系统”。

当前本地分支为 feature/slock-like-webui，工作区有未提交改动。 因此本文描述的是“本地正在演进中的真实状态”，不是干净 release 或 main 分支说明。

2. 课程脉络如何落到现在

课程不是“理想教程”，而是一条真实演化链：从工具调用，到 CLI 工程化， 到多猫协作，再到知识、记忆、Pack、门禁。现在本地仓库里的结构，基本都能在课程里找到根。

课程阶段解决的问题现在本地对应结构
第 0-2 课：工具与 CLI AI 从聊天到能干活；SDK 不够，转向真实 Agent CLI；处理 stderr、进程、Redis 隔离。 packages/api/src/domains/cats/services/agents、各 provider service、CLI spawn、runtime worktree、Redis 脚本。
第 3-5 课：元规则、A2A、MCP 回传 让猫不是工具，而是能主动说话、互相传球的协作者。 cat-cafe-skills/refs/shared-rules.md、callback-*.ts、packages/mcp-server/src/tools、A2A route/callback。
第 6 课：生产安全 AI 能执行命令后，数据安全和危险操作必须有硬护栏。 Redis 防护、危险操作 guard、preflight、备份恢复脚本、治理规则。
第 7-8 课：平台化与 Session 从 coding tool 到生活/平台；Rich Blocks、PWA、Whisper、Session Chain。 Rich components、visibility/whisperTo、session-chain routes/tools、ContextHealthBar。
第 9-11 课：上下文、知识、语音 保证 Agent 做的是你真正想要的；知识不腐；猫能听能说。 docs/features、evidence.sqlite、packages/api/src/domains/memory、TTS/ASR sidecar service。
第 12-15 课：无 Boss、闭环、记忆、纪律 从单次交付走向长期团队治理：没有 Boss Agent，靠对等判断 + 结构化执行。 Pack、家规、Feature lifecycle、Quality Gate、Merge Gate、A2A 球权、observability、AppShell。
课程与本地现状的关系： 第十五课还停在 149 个 Feature 阶段；本地已经到 193 个 Feature， 说明现在的重点已经从“证明三猫协作可行”，推进到“开源产品化、图书馆记忆、Pack 生态、Console 外壳、A2A 治理”。

4. 运行时总架构

Clowder 的运行可以理解成三层：模型层、Agent CLI 层、平台层。 模型负责推理，CLI 负责工具/文件/命令执行，Clowder 平台负责身份、路由、记忆、队列、门禁、审计。

关键设计思想

判断去中心化

没有 Boss Agent。多只猫可以独立判断、互相质疑、传球、review。

执行结构化

队列、active slot、session、hooks、worktree、Redis、门禁保证执行不乱。

知识可追溯

Feature、ADR、Lesson、Evidence、Library 让系统不是每次从零开始。

8. 消息与气泡管线

F183 是当前架构里非常重要的收敛点。它不是一个 UI 小修，而是把“气泡裂了、不见了、F5 才出来、发完才出来”的长期问题，收敛成一套消息管线架构。

为什么气泡以前容易出 bug

  • Redis MessageStore、Redis DraftStore、IndexedDB、Zustand/Ledger 多个真相源竞争。
  • OUTER invocationId 和 INNER invocationId 混用，不同 provider 路径补丁很多。
  • 消息写入口太多，stream/callback/draft/queue/hydration/replace/provider transform 各走各的。
  • WebSocket fire-and-forget，长 invocation 下会有 gap 和 catch-up 问题。
  • hydration merge 策略过复杂，每加一种消息 origin 就可能漏 case。

F183 的收敛方案

机制作用
Stable identity稳定身份收敛为 (catId, invocationId, bubbleKind)。
BubbleReducer / Single Writer所有 stream/callback/done/error/tool/background path 尽量统一进 reducer。
Thread-scoped seq实时事件带 seq，客户端发现 gap 后 catch-up。
IDB fallbackIDB 降级为离线首屏 fallback，在线 hydrate 时 server history authoritative。
Invariant gatedev/runtime 检测 duplicate stable identity、phase regression、canonical key split。
Replay harness用历史 fixture 回放，避免新路径再引入旧 bug。
这就是课程第十五课“速度来自纪律”的具体例子：不是靠说“以后小心气泡”，而是把消息身份、写入口、回放、断言、catch-up 全部工程化。

9. A2A 与球权协议

第十二课讲“没有 Boss Agent”。但没有 Boss 不等于没有秩序。 F167 正在把多猫协作里的“传球、接球、退球、升级、持球”做成运行时协议。

当前要解决的 A2A 问题

问题表现对应治理
漏传球该 @ 的时候没 @，链条断掉。早期 F064 已覆盖一部分。
乒乓球两只猫反复 @，但没人真正干活。F167 L1 same-pair streak 警告/熔断。
虚空传球说“我来做”，但实际把球传走或没人接。球权出口检查、接/退/升三选一。
角色错配让 designer 写代码、让不合适的猫接任务。角色适配门禁。
真持球无执行层猫说“我继续做”，CLI 退出后没人再唤醒。hold_ball MCP：有界持球 + 自动唤醒。
假终局review 给了结论就停，author 没收到下一步。Forced-pass guard：结论后默认必须传球。

球权协议的本质

每次猫输出结尾，都要回答： 1. 球在我手上，我继续执行什么？ 2. 球传给谁？为什么是它？ 3. 我做不了，退回/升级给谁？ 4. 需要 CVO 决策吗？ 不能只说状态，必须给出可执行的下一棒。

10. 记忆与图书馆

课程第十课讲“别让 AI 随地大小拉 markdown”，第十四课讲“三层记忆与自我进化”。 本地现在已经从 F102 的项目 evidence 系统，推进到 F186 的图书馆记忆。

F102：项目证据库

  • evidence.sqlite 是编译产物，不是真相源。
  • 真相源仍是 docs/features、docs/decisions、docs/public-lessons.md 等文档。
  • 支持 lexical、semantic、hybrid 三种检索。
  • 支持 summary segments、summary state、edges、embedding meta。
  • 通过 IKnowledgeResolver 做联邦检索与 RRF rank fusion。

F186：图书馆记忆架构

F186 把记忆从“项目附属能力”升级为“多域 Collection 图书馆”。 核心抽象是： 

Collection = truth_source
           + owner
           + scanner
           + authority_ceiling
           + review_policy
           + index_policy
组件职责
LibraryCatalogCollection 注册表，只存元数据和路由策略。
LibraryResolver根据 dimension/collections/sensitivity 做 fan-out、RRF 聚合、分组返回。
ScannerFlatScanner、StructuredScanner、RepoScanner，把 truth source 编译进索引。
SecretScanner外部 Collection chunk/embed 前先扫 secret，避免把密钥入库。
GraphResolverTyped graph，支持 related/evolved/supersedes/invalidates 等关系。
Knowledge Feed候选知识先进入审核队列，再 materialize 到真相源。
重要边界： 外部 Collection 内容是 evidence data，不是 instruction。也就是说，外部项目里的 AGENTS.md、规则、笔记不能改变猫的系统提示词或工具权限。

11. Pack 与 Growth

F129 / ADR-021 是当前“新思路”的核心。 它把 Clowder 从一个具体的 Cat Café，推向“可分享的 multi-agent 协作世界”。

产品公式

Experience = Me × Pack + Growth
  • Me：用户自己，本地私有，不打包。
  • Pack：可分享的协作世界定义，像文化种子。
  • Growth：用户和猫一起长出来的私有关系/记忆，不能直接外发。

Pack 不是 Plugin

PluginPack
给 Agent 加一个工具/API。定义一群 Agent 如何在某个世界里协作。
能力包。协作世界。
关注“能做什么”。关注“谁是谁、怎么协作、什么不能做、知识在哪里”。
常常是运行时代码。前 8 层尽量 YAML/Markdown 零代码，最后 capability 才是代码。

Pack 内部结构

my-pack/ ├── pack.yaml ├── masks/ ├── guardrails.yaml ├── defaults.yaml ├── workflows/ ├── knowledge/ ├── expression/ ├── bridges/ ├── world-driver.yaml └── capabilities/

安全边界

  • Pack 不原样注入 system prompt，必须 schema → compile → canonical prompt block。
  • guardrails 只能加严，不能放宽 Core Rails。
  • 未知字段 fail-closed。
  • Growth 私有，不能作为 Pack 直接外发。

家规的作用

shared-rules.md 是三猫共用规则真相源，会被 SystemPromptBuilder 编译摘要注入每只猫。 它不是“提示词装饰”，而是整个团队的社会契约。

  • Rule 0：规则是边界，不是全部，保留判断力。
  • P1：面向终态，不绕路。
  • P2：共创伙伴，不是木头人。
  • P3：方向正确 > 执行速度。
  • P4：单一真相源。
  • P5：可验证才算完成。
  • Magic Words：脚手架、绕路了、喵约、星星罐子、第一性原理等手动拉闸词。

13. 外部连接、MCP、语音

Clowder 已经不只是浏览器里的聊天界面，而是在向“多入口、多设备、多服务”的平台发展。

外部消息与 connector

  • F088 Chat Gateway：飞书、Telegram 等外部聊天平台进入 Cat Café thread。
  • Connector Binding：外部 chat 与内部 thread 的映射。
  • Callback Auth：外部回调鉴权、持久化、降级与可观测，对应 F174。
  • WeCom / Feishu / Telegram / GitHub 等入口逐步接入。

MCP Portable Provisioning

F145 解决的是“新机器 clone 后 MCP 不该手工一个个挂”的问题。 它区分声明式期望态与本机解析态：

  • capabilities.json 不再存机器绝对路径。
  • .cat-cafe/mcp-resolved.json 存本机解析结果。
  • pnpm mcp:doctor 输出 ready/missing/unresolved。
  • ACP/Gemini 可以自动获得内置 cat-cafe* MCP servers。
  • 用户项目自己的 .mcp.json 也可以 merge 到 ACP session。

语音与服务

课程第十一课讲 ASR/TTS。当前本地有 service manifest 与 sidecar 管理： Whisper/Qwen ASR、TTS、Embedding、LLM postprocess 等都通过 scripts/services 和 /api/services 管理。

14. 运维、可观测、安装

可观测性 F153

F153 从 OTel SDK、metrics、health check，一路做到 Hub 内嵌 trace tree、metrics history、burn-rate 告警。 现在它的定位是 descriptive observability plane：先回答“发生了什么”，不是做质量评分。

  • TelemetryRedactor：凭证、业务正文、系统标识符分级脱敏。
  • MetricAttributeAllowlist：防止高基数标签爆炸。
