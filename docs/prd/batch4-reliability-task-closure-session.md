# PRD：批次 4（第一波：4-A / 4-B / 4-C）

> 一句话：把这两天真实流过血的三类事故——**权限静默瘫痪、任务有始无终、会话撑爆断刊**——各自装上"监测 + 自愈 + 大声报警"三件套。第二波（4-D 责任田+图书管理员、4-E 小件打包）另立，不在本 PRD。

## 0. 素材来源

- 实证事故：EPERM 静默死（07-25 推特日报）、芝芝认领挂机（07-26）、荧荧 25MB 会话卡死断刊 6 场、in_review 无人验收（Raft 同款 29 票卡 16）；
- maka 二次深挖 4 项强推蓝本（goal-evaluator 卡壳计数器/外部裁判、waiting 指数退避、root-authority 属主锁、启动即校验+错误转人话）；
- 已上线的地基：认领闲置唤醒器（01e82b75）、Terminal Invariant、错误分类表、任务创建对齐 Raft。

## 4-A 可靠性补完：权限哨兵 + EPERM 分类 + 属主锁

### 问题
07-25 晚 macOS TCC 收权后：猫的执行被静默杀死/CLI 起不来，**没有任何主动告警**，靠铲屎官发消息试出来的；EPERM 退出还被当"瞬时故障"白白重试两次。

### 方案
1. **权限哨兵**：api 启动时 + 每小时，对治理注册表里所有已确认项目目录做读探测（open 一个已知文件），对 Clowder 数据根做写探测。失败 → 大厅发零 token 系统告警卡（中文，含修复指引"终端跑 pm2 update / 检查完整磁盘访问权限"）+ 进 Activity；恢复后发一条解除通报。同一目录告警去重（状态未变不重发）。
2. **EPERM 智能分类**：claude/codex CLI 启动即退且 stderr 含 EPERM/permission → 错误分类新增 `permission_denied` 类：**不重试**（现在按 transient 重试 2 次纯浪费），线程里贴带修复指引的卡，并触发哨兵立即复检。
3. **属主锁**（maka root-authority 模式）：Clowder 数据根（.cat-cafe）放属主 marker（pid + dev/ino 身份校验），api 启动时校验——防"桌面 App 与 PM2 双开"这类事故（07-24 真实发生过）。stale 锁（进程已死）自动接管；冲突时拒绝启动并人话报错。

### AC
- A1 手动收权模拟（chmod 000 测试目录）→ 1 小时内大厅出现告警卡，恢复后出现解除通报；
- A2 CLI EPERM 退出 → 零重试、线程可见带指引的卡、错误分类记 `permission_denied`；
- A3 第二个 api 实例启动 → 被属主锁拒绝并输出人话；杀掉持锁进程后可正常接管；
- A4 golden 全绿，全部功能各自带 env 开关（默认开）。

## 4-B 任务闭环：in_review 验收人 + 超时升级 + 卡壳计数器 + 外部裁判预审

### 问题
任务流"完成"侧没有闭环：置 in_review 后没有验收人、没有超时机制（Raft 实测 29 票卡 16 票）；doing 中"在跑但原地转圈"没人发现（已上线的闲置唤醒器只管"根本没在跑"）。

### 方案
1. **验收人字段**：task 增可选 `reviewerId`（猫 id 或 'human'）。缺省规则：创建者是人 → human（=你）；猫拆的子票 → 父票 owner。置 in_review 时通知验收人（human=大厅+Activity；猫=唤醒投递，复用闲置唤醒器管道）。
2. **in_review 超时升级**（maka waiting 退避模式，人化节奏）：4 小时无验收 → 提醒验收人一次；24 小时 → Activity 置顶升级 + 大厅通报"票 #N 等验收已 1 天"。每票最多 2 次提醒（防轰炸）。
3. **卡壳计数器**（maka consecutiveNoProgress 模式）：doing 且**有**活跃执行的任务，以"任务事件/进度上报"为进展信号；连续 N 轮执行结束都无任何任务侧进展（默认 N=3）→ 自动置 blocked，原因写"连续 N 轮无实质进展"，通知 owner 与你。与闲置唤醒器互补：唤醒器管没在跑，计数器管空转。
4. **外部裁判预审**（maka GoalEvaluator 模式，v1 保守版）：猫置 in_review 时，用便宜模型（sonnet）按任务 why/AC 自动核一遍证据（测试输出/diff/链接是否存在且对题），产出"预审意见"附在任务卡上供验收人参考。**v1 不自动打回**（只出意见）；自动打回作为 v2 开关另议。每票预审一次，控成本。

### AC
- B1 猫置 in_review → 验收人按缺省规则被通知，任务卡显示验收人与预审意见；
- B2 构造 4h/24h 超时 → 两级提醒各触发一次且不超过 2 次；
- B3 连续 3 轮执行无任务进展 → 自动 blocked 且原因可见；
- B4 预审意见在卡上可见，token 消耗 ≤1 次 sonnet 调用/票；
- B5 golden 全绿；所有新行为 env 可关。

## 4-C 会话膨胀治理（自研，maka 已证实无解）

### 问题
荧荧的 CLI 会话文件累积到 25MB：每次被定时任务叫醒，光加载历史就卡死，1 小时超时，断刊 6 场。maka 同样一次性整读会话文件——这题业界抄不到，只能自研。

### 方案（按落地顺序）
1. **定时任务每场新会话**：scheduler 派单不复用 cliSessionId（宪宪诊断时点名的治本项）。上下文靠既有 session-chain digest 机制找回（孟加拉猫冷启动 onboarding 已验证此路可行）。
2. **体积监控**：session 绑定/结束时记录文件体积；超软阈值（默认 4MB）→ 大厅告警"XX 的会话已 XMB，建议轮转"；超硬阈值（默认 10MB）→ 下次派单强制新会话（等同 1 的机制扩展到所有场景）。
3. **轮转归档**：强制新会话前，把旧会话摘要（digest）沉淀进 session-chain / thread 存档消息，保证"换脑子不丢记忆"。
4. （v2，不在本批）分段加载/读预算——maka 的 header+tail 预算模式只解决列表扫描，单会话整载的分段读留待后续。

### AC
- C1 定时任务连续两场 → 两个不同 cliSessionId，第二场能引用第一场 digest 里的关键结论；
- C2 构造超软阈值会话 → 告警出现；超硬阈值 → 下次派单自动新会话且旧会话 digest 已归档；
- C3 推特日报连跑 3 场无超时（真实验收，观察窗口内）；
- C4 golden 全绿；阈值 env 可调、机制 env 可关。

## 瘦身修订（2026-07-26，基于 Raft 第六轮访谈 + 铲屎官"过度设计"担忧）

第六轮访谈（raft-习惯.md）证实：Raft 在这三块的平台机制**远比我们计划的少**——没有健康自检、没有验收人字段、没有超时、没有空转检测、没有自动预审，会话治理靠平台压缩+记忆纪律且"从没痛过"。结合我们自己刚发生的唤醒器风暴（机制上得急、真实存储路径没测透），按"血案实证才立机制，Raft 明确推荐才优先"重排：

### 砍掉/降级（过度设计确认）
| 原计划 | 处置 | 理由 |
|---|---|---|
| 4-B 外部裁判预审 | **砍**（进 backlog v2） | Raft 没有也没推荐；其人肉 gate 文化（验收人重跑证据）才是被实证的；每票一次模型调用的成本换"参考意见"性价比存疑 |
| 4-B 卡壳计数器 | **缓**（先修好已上线的闲置唤醒器再说） | Raft 无空转检测靠纪律；我们的唤醒器已覆盖最痛场景且刚证明"急上机制"的代价 |
| 4-A 每小时权限哨兵 | **降级为：启动自检一次 + EPERM 失败时按需复检** | Raft 连自检都没有；我们的痛根在 TCC（pm2 update 后应绝迹），常驻轮询是为罕见事故常年付费 |
| 4-C 硬阈值强制轮转+归档 | **缓**（先观察软告警数据） | "每场新会话"已治断刊根因；轮转机器是为尚未复现的第二形态提前造的 |

### 保留（Raft 明确推荐 or 我方血案实证）
1. **验收人字段 + 超时两级提醒**——Raft 原话"这两个字段+一个计时器是便宜的平台级修复，别像我们靠自觉"（其 #1 推荐）；
2. **新增：assignee 失能 → 名下 in_progress 票自动打标**——Raft "别学我们"清单点名（#401 冻死票现状），实现便宜（挂在错误分类的失能信号上）；
3. EPERM 分类不重试 + 错误原文直出（今天已上线大半，收尾即可）+ 治理注册表查询韧性修复（今天的实证 bug）；
4. 闲置唤醒器护栏修复（隔离 Redis 红→绿）——重新开启的前提；
5. 属主锁最小版（我方 7-24 双开真实事故）；
6. 定时任务每场新会话 + 体积软告警（断刊 6 场实证）。

### 修订后体量
原三路并行约 8-12 个机制件 → **瘦身后 6 件小活**，预计一波 sonnet（2-3 路）一个部署窗口完成。Raft 访谈同时确认了我们两个已做对的方向：上下文水位指标（理智线）、记忆过期提醒——不动。

## 第七轮访谈参数落定（2026-07-26，全部照抄 Raft 实测/设计咨询，原始材料 raft-第7轮.md）

### 4-B 任务闭环（最终版）
| 项 | 参数/规则 | 来源 |
|---|---|---|
| reviewer 字段 | **只建一个字段**（gate 预验/人类终审双字段砍掉，终审=纪律层） | Q2 |
| 缺省指派 | 人建的票→常设 gate（可配置的 gate 猫，未配置时=human；**不是建票人**）；agent 子票→继承父票 reviewer；**执行者永不 review 自己的票（服务端校验）** | Q2 |
| 提醒分轨 | 按验收人类型分轨不按票分级：gate（猫）轨=24h 私提醒**验收人**；human 轨=48h 私提醒 → +48h 频道内可见@owner → 7-14 天**状态动作**（自动降回 doing+通知双方）。三级封顶，第三级必须是状态动作不是更响的闹钟 | Q1 |
| 失能打标 | 状态异常**持续>30min**（防闪断）→ 名下 in_progress/todo 打标 → 通知 owner+票所在频道（不 DM 轰炸）→ **不自动转派**（转派=人/gate 决定+带交接）；恢复自动清标但留"真空期"事件记录 | Q3 |
| 验收证据自动化（替代已砍的外部裁判） | 只做 Raft gate 点名的四件：①in_review 时自动锚 commit sha/diff stat/文件清单进票 thread ②自动重跑提交者声明的测试命令（隔离环境）附原始输出 ③静态扫描（二进制/裸控制字符+diff 密钥形态）④验收动作留痕。**永不自动化**：语义一致性判断/对抗性边界推演/范围裁定 | Q5 |

### 闲置唤醒器重开参数（修 bug 同批调整）
- 首次 nudge：15 分钟 → **2 小时**（Raft 实测人肉节奏：小票 2-4h、调研票 24h；我们的 15min 激进了 8 倍，也是风暴的放大器）；
- nudge 文案改为"进度或阻塞说一句"式（要状态不是催促——"请尽快"只会得到"在做了"）；
- 保持：2 次封顶+第三步升级人工（Raft 收尾确认"升级判断留给人，做成机制会误伤深度工作"）。

### 4-C 会话治理（方向修正）
- Raft 单会话 207MB 零问题——关键不在体积在**访问模式**（runtime 从不整文件加载，transcript 只是 append-only 审计层）。
- 修正：**不定体积上限**；实施顺序改为 ①排查我方 25MB 卡死的全量加载路径（若在第三方 CLI 的 resume 内部无法改→"每场新会话"就是唯一杠杆）②定时任务每场新会话 ③4MB 软告警仅作观测（不触发任何动作）。

### 4-A 补充（资源卫生，对应泄漏实例事故）
- 照抄 Raft 测试隔离纪律：测试起的进程 trap 全覆盖（正常/异常/超时退出全 kill）+ 测试脚本收尾断言"无残留进程"；构建产物与 live 分离沿用我方现有窗口纪律。Raft 自己 daemon 无监控无定期重启（"裸的"）——佐证每小时哨兵砍得对，启动自检一次即可。

### 落定后的待办清单（三路 sonnet）
- A 路：启动自检 + EPERM 收尾 + 注册表韧性 + 属主锁最小版 + 测试进程 trap/断言；
- B 路：reviewer 字段与缺省规则 + 分轨提醒（3 级封顶）+ 失能打标 + 验收证据自动化四件（①③④先行，②隔离重跑其次）；
- C 路：唤醒器护栏修复（隔离 Redis 红→绿）+ 参数重调（2h/文案）+ 会话全量加载路径排查 + 每场新会话 + 软告警。
