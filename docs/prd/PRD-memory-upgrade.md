# PRD：Clowder 记忆系统升级（四层模型落地）

## 1. 摘要

把 Clowder 的记忆能力按"四层模型"（画像/记忆/知识/运行状态）补齐短板：给记忆系统立测量尺、让互相矛盾的记忆能合并和退休、给用户画像装上人审界面、治好长活频道 session 撑爆卡死的病、把刚接入的 Obsidian 知识库运维闭环。原则是**复用已有资产、不引外部库**——调研证明我们缺的是接线，不是架构。

## 2. 干系人

| 谁 | 角色 | 说明 |
|---|---|---|
| 铲屎官（yangcyyang） | 决策 + 最终验收 | 拍板每批开工；画像人审 UI 的唯一使用者 |
| Fable 主协调 | 编排 + 逐项验收 | 派工 sonnet、复跑测试、控制爆炸半径 |
| sonnet 执行猫 | 实施 | 每个 feature 一个独立 agent |
| 荧荧（grok）、墨墨（kimi） | 灰度对象 | session 治理灰度先上荧荧（正是事故猫）；评测回放用真实猫历史 |

## 3. 背景：为什么是现在

三件事同时发生，把"记忆升级"从想做变成该做：

1. **生产事故**：荧荧的 CLI 原生会话文件积累到 25MB，每次被定时任务叫醒都在加载全历史中卡死，推特日报连断 6 场。调研确认这是结构性缺口——Clowder 管得住自己的会话压缩，管不住各家 CLI 自己的续接历史。
2. **调研结论落地窗口**：拆解 Mem0/Memobase/Zep/Letta 发现（docs/research/memory-absorption.md），我们已有三件别人家的"招牌"（打分公式、失效字段、多源知识联邦），差的只是接线到猫记忆和画像两层——成本从"引入一套系统"降到"每件 2-6 天"。
3. **积压的债**：用户画像人审候选队列一直没有界面（候选只进不出）；Obsidian 知识库刚挂载但索引不自动刷新（本周已过期 11%，手动补过一次）。

## 4. 目标与关键成果

**目标**：让猫"记得住、记得对、醒得快"——用户交代过的事不用重复说，记忆互相打架时有裁决机制，长活频道永不因历史过长而瘫痪，而且**一切在省钱红线内**（不破坏 KV-cache 缓存布局）。

**关键成果（KR，全部可量化验收）**：

| # | 关键成果 | 量尺 |
|---|---|---|
| KR1 | 记忆系统第一次有测量基线 | 评测集 ≥30 条查询（覆盖记忆召回/画像分类/会话体积），基线数字落档 |
| KR2 | 记忆冲突有裁决 | 影子模式跑 2 周，合并/失效建议的人工采纳率达到批次 1 现场定的阈值后才转强制档 |
| KR3 | session 撑爆根治 | 灰度猫唤醒耗时从"小时级超时"回归分钟级；不再出现超限体积的原生会话文件 |
| KR4 | 画像人审闭环 | 候选队列积压清零，且新候选平均滞留 ≤7 天 |
| KR5 | 知识库保鲜 | 索引新鲜度 ≤24 小时（定时重建），不再需要人肉触发。**检索能力已实证**（2026-07-25：用猫的检索入口限定该库搜索，命中 vault 原文；词法模式确认可用，语义模式覆盖待 F-H 确认）——不需要从零建，需要补运维 |
| KR6 | 频道精华回流知识库 | 频道/讨论里的精华内容能一键沉淀为知识库笔记（见 F-I），落入 vault 的"00待确认"收件区，经你在 Obsidian 里审核归位后被下次索引收录 |
| 红线 | 省钱底线不破 | 金丝雀猫的缓存命中率不因任何记忆改动下降（ADR-024 布局约束全程生效） |

## 5. 用户与约束

**用户就一位**：铲屎官本人（单用户、多猫编排的个人 AI 工作台）。受益的"间接用户"是十几只猫——它们的工作连续性直接决定铲屎官的使用体验。

**硬约束**：
- 本地部署，多 CLI 供应商编排（Claude/Kimi/Grok/Codex/Gemini），不能假设任何模型层能力；
- ADR-024 缓存布局：每轮易变内容只能进队尾，静态前缀一个字节不能动；
- 记忆含个人信息：写入必须过晋级门（不允许任何绕过档位的旁路），知识库秘密隔离机制保持生效；
- 人审带宽有限：默认档位宁保守勿激进（影子先行，强制后置）。

## 6. 价值主张

| 用户的痛 | 升级后 |
|---|---|
| 同一个偏好要跟每只猫反复交代 | 画像层结构化 + 人审闭环，说一次全体猫共享 |
| 猫的记忆越用越矛盾，行为飘忽 | 冲突自动检测 → 给出合并/退休建议 → 人一键裁决 |
| 定时任务频道跑几周就卡死 | 会话超限自动轮转，要点蒸馏进记忆，新会话轻装上阵 |
| 一万篇笔记的知识库猫看不到最新的 | 每日自动重建索引，猫随时检索到最新知识 |
| 不知道记忆系统是变好还是变坏 | 有基线、有量尺，每次改动有数字对比 |

**为什么不直接用 Mem0/Memobase**：两者都假设"记忆往提示词前面拼"，与我们的缓存省钱布局直接冲突；我们的晋级门灰度纪律（关/影子/强制三档）比它们"LLM 判定后直接写"更保守；引整库=并行维护第二套记忆语义。抄动作，不抄库。

## 7. 方案

### 7.1 界面（仅一处新界面）

**画像编辑区（铲屎官已拍板，提前实施）**：成员配置里 **cy（Owner）自己的编辑弹窗**（现有"身份信息/别名与@路由"两区之后）新增"**铲屎官画像**"区——偏好/硬约束/账号级事实三个可编辑文本框，直接读写个人名片 USER.md，保存即生效（对走新布局的猫下一次派单可见）。Owner 本人编辑 = 最终权威，不过人审队列；猫提议的新条目才进队列。附 token 预算提示（超 1k 提示截断风险）。

**画像人审页**：候选列表（待审记忆条目 + 来源猫 + 建议动作）+ 两个按钮（批准/驳回）+ 冲突条目附"合并建议文案"可一键接受。**入口位置（铲屎官已拍板）**：频道页右上角工具栏图标区最左侧空位（下载/视图/设置那排图标旁），全局入口、带待审数量小红点。

**频道精华沉淀入口（F-I 配套，铲屎官已拍板）**：**改造现成的"沉淀为知识"弹窗**（KnowledgeCaptureModal.tsx，频道页右上工具栏已有入口，现有 Feature/Lesson/Decision 三张类型卡）——加第四张类型卡"**知识库**"，选它则生成的笔记投递到 Obsidian vault 收件夹而非 Clowder docs 目录。类型/标题/摘要的表单流程原样复用，零新界面。消息右键菜单后续加"沉淀到知识库"项 = 预填选中内容打开这个弹窗的快捷方式。

### 7.2 功能清单（8 项，每项独立可验收）

| # | 功能 | 一句话 | 验收标准 |
|---|---|---|---|
| F-A | 评测尺 | 扩展已有的两套评测件（知识检索 gold set + 排序指标工具），覆盖记忆召回与画像分类，用真实猫对话回放 | ≥30 条查询 + 基线数字落档 |
| F-B | 冲突消解两动作 | 晋级门的"搁置"细分为"可合并"（重叠信息→合并文案建议）和"该退休"（矛盾→建议旧条目失效） | 影子模式建议准确率达标才转强制 |
| F-C | 失效字段扩展 | 把已验证的 `invalid_at/superseded_by` 字段从知识层扩展到猫记忆和画像（冲突触发，不按时间自动过期） | 冲突检测命中时正确标记，人审确认后生效 |
| F-D | 记忆召回排序 | 把已有的显式打分公式扩展到猫的 notes 记忆召回（当前零排序） | 评测集上召回命中率相对基线不降且有提升 |
| F-E | 画像槽位化 + 人审 UI | 画像从自由文本升级为"固定三大类 + 可扩展子槽位"；配套 7.1 的人审页 | 存量迁移零丢失 + 队列积压清零 |
| F-F | 猫主动写记忆工具 | 新增记忆写入工具让猫对话中主动沉淀，内部强制走同一个晋级门 | 与自动回写共享同一决策逻辑（单元测试锁死） |
| F-G | CLI 会话轮转 | 原生会话超体积/超轮次触发强制轮转：先蒸馏要点入两层记忆，新会话只带摘要 | 灰度猫（荧荧）唤醒耗时回归分钟级 |
| F-H | 知识库运维闭环 | 索引定时重建 + 确认语义检索是否启用 + 排查 237 篇未索引 | 新鲜度 ≤24h，排查结论落档 |
| F-I | 频道精华沉淀回知识库 | 消息右键/thread 一键"沉淀到知识库"：把选中内容蒸馏成带来源链接的笔记，**只写入 vault 的"00待确认/clowder-inbox/"收件夹**（挂载仍是只读原则——绝不碰你已有笔记，只投递新文件到收件区），你在 Obsidian 里审核后归位，下次索引重建自动收录 | 沉淀一条真实讨论 → 收件夹出现规范笔记（含 frontmatter+回链）→ 重建后可被猫检索到 |

### 7.3 技术要点（全部复用，零新依赖）

打分公式、失效字段、冲突检测器、晋级门、会话压缩阈值模式、自动回写器——全部是仓库里已验证的组件，本次只做扩展接线。不引入向量库、不引入外部记忆服务。

### 7.4 假设（待验证，逐条标注在实现中）

1. 字符串相似度足以支撑合并建议的初版准确率（不够再上语义判定）——影子期验证；
2. 会话轮转不破坏各家 CLI 的续接语义——灰度期验证；
3. 人审 UI 的使用频率足以清空积压——若否，增加"低风险自动批准"档位提案。

## 8. 发布计划（相对时间，无承诺日期）

| 批次 | 内容 | 预估 | 门槛 |
|---|---|---|---|
| 批次 0（可并行） | F-H 知识库运维闭环 | 2-3 天 | 无依赖，随时可做 |
| 批次 1（第一版） | F-A 评测尺 | ~1 周 | 无依赖；**是后续所有批次的前置** |
| 批次 2 | F-B + F-C 冲突消解 | ~1 周实施 + 2 周影子观察 | 依赖批次 1 的量尺 |
| 批次 3 | F-E + F-F + F-G + F-D + F-I | ~2 周 | 依赖批次 2 升级后的门逻辑；F-I 另依赖右键菜单（前端在飞件）落地 |

> **名词解释——"影子模式"**：系统把"我本来会怎么改这条记忆"的建议**只记在清单里，不真的动手**。你隔段时间看一眼清单，标"建议得对/不对"。等它的建议准确率过了批次 1 定的及格线，才把开关拨到"强制档"让它真动手。相当于新员工先试岗打分、后转正——试岗期它做错什么都不会造成任何实际影响。

**第一版（批次 0+1）的定义**：不改任何行为，只加度量和运维自动化——零风险起步，为后面每一刀提供数字依据。

**明确不做**：整库引入 Mem0/Memobase；Engram 参数记忆与多模态视觉记忆（与多 CLI 编排架构前提矛盾）；照搬 LOCOMO 学术评测协议（其基准数字本身存在公开争议，只借鉴方法论）。
