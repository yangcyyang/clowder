# Clowder 功能全量盘点 + 裁剪建议

> 用途：给铲屎官做"哪些功能不必要、可以剪掉"的决策底稿。
> 数据来源：探查 agent 全库扫描（149 个 route 文件、192 个前端组件、258 个注册 env）+ 我对生产真值的复核（PM2 进程环境实测）。
> 怎么读：第一节是别动的主干；第二节是全量清单（供你逐条过）；第三节是我的裁剪判断，分"建议砍 / 建议冻结或加闸 / 观察后再定 / 明确别砍"四档，每条带依据。

## 一、核心主干（不在裁剪讨论范围）

频道消息流 + Thread 系统（含 thread-first、Edit=Branch）、任务系统（CRUD/状态机/认领/队列）、@提及路由（串行/并行）、治理门与能力票据（生产 enforce，安全关键）、9 家 Provider 适配层、模型扫描 5 来源、Session 链/封印/交接、记忆主干（SQLite 证据库+索引）、统一调度 TaskRunnerV2、Hub 设置 12 分区、桌面打包。——这些是产品本体或安全地基。

## 四、顺手发现的技术债（不裁剪也该修）

1. **未注册 env**：thread-address 两个 CLOWDER_ 变量生产在用却不在 env-registry（违反注册表契约，Hub 不可见）；

## 五、二审：第一性原理 × Raft 对标（2026-07-26，应铲屎官要求）

一审是"从代码证据看谁没人用"；二审换两个更根本的透镜重新过一遍。**二审结论与一审冲突处，以二审为准**；末尾附合并后的最终清单。

### 5.1 第一性原理：Clowder 到底是什么

从你的真实用法倒推（不从代码倒推）：**一个人 + 一队异构 CLI agent，完成真实工作**。核心回路只有一条：

> 人说话 → 路由到对的猫 → 猫在真实环境执行 → 产出可验收的证据 → 人/gate 验收 → 沉淀记忆。

平台的全部合法性来自五个不可外包的职责：①**路由与会话**（消息/thread/@/队列）②**执行编排**（provider 适配/spawn/恢复）③**可靠性与安全**（别静默死、别越权、出事能查）④**记忆与上下文**（换脑子不失忆、KV 缓存省钱）⑤**任务闭环**（建票/认领/验收，批次 4 在补）。

**其余一切，要么服务这五条，要么是负资产。**这就是二审的全部判据。

### 5.2 Raft 对标的三个结构性启示（对结构不对逐条功能）

1. **Raft 机制极简，闭环靠纪律和文化**（验收人重跑证据、同事巡板）——复杂度花在纪律上是零维护成本，花在代码上是持续收税。"Raft 没有"的机制我们要立，必须血案实证——这已是家规，不重复。
2. **Raft 的宿主白送了很多东西，Clowder 的猫跑在裸 CLI 上**——这是对标时最容易砍错的一类。对应关系：Raft 平台压缩 ↔ 我们的 session 链/封印/交接胶囊/理智线；Raft MEMORY 注入 ↔ 我们的 agent 记忆自动写入+晋升门；Raft 有界读取/freshness-hold ↔ 我们的分层上下文/ADR-024/新鲜度闸。**这一类"Raft 没有"恰恰因为它宿主有，我们必须自建——二审后比一审更确定保留。**
3. **Raft 零产品化包装、零娱乐**。Clowder 的这一整层（游戏/世界引擎/成就/投票/训练营/首跑任务/场景指引/演示页）合计约 1.6 万行。第一性原理只问一句：**今天 Clowder 的用户是谁？**

### 5.3 一个必须你拍板的战略分岔

Clowder 是"你一个人的生产力工具"还是"要对外发布的产品"？这决定一整档的去留：

- **工具答案**：包装层（训练营 709 行 api + 场景指引 1820 行 api + 首跑/引导前端约 1.2k 行）整层出清；
- **产品答案**：onboarding 类保留，只砍娱乐层。

我的建议是中间路径：**按"现在是工具、未来可能是产品"处理**——娱乐层（游戏/世界/成就/投票）现在就砍；包装层（训练营/首跑/指引）**冻结不删**（标注不维护，等发布决心明确再复活）。理由：first-run-quest 有他人未提交的改动=有人在推，删了会撞车；冻结的成本是零。**但"是谁在推、为什么"这个问题你得先问清楚**——如果连你都不知道为什么在做 onboarding，那答案已经出来了。

> **【2026-07-26 铲屎官拍板】工具答案成立**：Clowder 定位是"我一个人的工具"，愿景=在平台上与多 Agent 对话，我派活给 Agent，Agent 能再派活给其他 Agent，最后合并回来汇报给我。据此：①包装层（训练营/首跑/场景指引）从"冻结"升为**砍**（first-run-quest.ts 因有在飞未提交改动，本窗口暂缓、下窗口收尾）；②愿景同时把 A2A 互调、多猫编排、任务闭环（批次 4-B 的 reviewer/合并汇报链）钉死为核心主干，不在任何裁剪讨论范围。裁剪执行即刻启动（Owner 口令"基于你的判断去砍掉对应的模块"）。

**新增的第一性收益（比省维护更硬）：**

猫侧工具面。mcp-server 的 67 个 `cat_cafe_*` 工具里，游戏动作、蒸馏、limb 等工具都混在默认工具集（server-toolsets.ts 实测）——**每只猫每次调用都背着这些工具的 schema**。砍功能=同步摘工具=每猫每次调用的上下文减负+误用面收窄。这是裁剪直接改善核心回路质量的部分，不只是"仓库干净了"。

### 5.5 二审后最终清单（合并一审，以此为准）

### 5.6 二审总结论

33 万行里，核心回路+其地基（含为裸 CLI 自建的上下文设施）大约占六成；砍+冻结合计约 2.6 万行（8%）听起来不多，但它们集中在**最没人看的角落**——正是排查事故时最花时间的迷路区，也是猫工具面里的死重。Raft 给的真正教益不是"少做机制"，而是**复杂度该花在纪律（零维护）还是代码（持续收税）**。二审后的产品边界一句话：**平台只做五职责+血案实证的机制，其余交给 SOP 和猫的判断力。**
